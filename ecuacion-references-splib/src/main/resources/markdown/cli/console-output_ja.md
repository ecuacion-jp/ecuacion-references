`ecuacion-splib-cli` はコンソールへの出力にタイムスタンプ付きの一貫した書式を使います。ここでは、正常時の出力・エラー時の詳細な出力・配布物としての注意点をまとめます。

## 正常な出力にタイムスタンプを付ける：`ConsoleUtil.printlnWithTimestamp`

`SplibCliApplication`自身も、`execute`呼び出し前後の「処理を開始します。」「処理が正常に終了しました。」（[クイックスタート](page?id=cli/quickstart&lang=ja)参照）にこれを使っています。アプリの`execute`内で同じ書式のログを出したい場合は、直接呼び出してください。

```java
ConsoleUtil.printlnWithTimestamp(false, "中間処理が完了しました。");
```

```
[2026-08-15 15:37:42] 中間処理が完了しました。
```

第1引数`isError`を`true`にすると、標準出力ではなく標準エラーに出力されます。

## エラーの詳細を見るには：`--verbose`

アプリが例外で失敗すると、デフォルトではスタックトレースを出さない簡潔なメッセージだけがコンソールに表示されます。アプリを`--verbose`付きで実行すると、この簡潔なメッセージに加えて、完全なスタックトレースが`System.err`にも表示されます。

CLIアプリは実行している本人が直接画面を見ているため、ログ出力ではなく画面への出力を基本としています。

## 参考：ログ出力の設定

それでもアプリとして常時ログファイルを残しておきたい場合（例：社内ツールで常にログを残したい）は、[クイックスタート](page?id=cli/quickstart&lang=ja)にある素の`<root level="OFF" />`の代わりに、自分のlogback-spring.xmlに独自のlogger/appenderを追加してください——`LogUtil.logSystemError`の呼び出し自体は既に行われているので、コード変更なしにそのまま機能し始めます。

## 配布時の注意：jarの中身は秘匿されない

`--verbose`はオプトインで、何もしなければコンソールにスタックトレースは出ません。とはいえ、「そもそも`--verbose`でスタックトレースをそのまま見せてしまってよいのか」という疑問はもっともです。

アプリ側で`main`メソッドが`SplibCliApplication.main`に渡す前に`args`から`--verbose`を取り除いてしまえば、この機能自体を黙らせることはできます。ただ、それにはあまり意味がありません。`java -jar your-app.jar`で配布するfat jar（依存関係を1つにまとめた実行可能jar）は、展開して各`.class`ファイルをデコンパイルすれば、ロジックのほとんどがそのまま読める配布形式だからです。アプリに秘匿性の高いロジック（社外秘のビジネスルールやアルゴリズムなど）が含まれるなら、それをfat jarのままクライアントに渡している時点で、`--verbose`の有無に関わらずリスクはすでに存在します。

秘匿性が要件になる場合は、`--verbose`を隠すのではなく、配布形式そのものを見直してください。

- GraalVMなどによるネイティブイメージ化 — バイトコードをそのまま渡さずに済むため、解析のハードルを大きく上げられます（解析を不可能にするわけではありません）。
- クライアント・サーバー方式への変更 — 秘匿したいロジックをサーバー側に残し、クライアントには結果だけを返すことで、ロジック自体を配布物に含めずに済みます。

`ecuacion-splib-cli`自体は「実行ファイルをそのまま配布して手元で動かす」利用形態を前提としており、上記のような配布形式の選択はアプリ側の設計判断になります。
