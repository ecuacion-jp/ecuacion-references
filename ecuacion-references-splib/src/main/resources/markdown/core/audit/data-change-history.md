The data change history keeps "which row was changed, when, by whom and how" for every insert, update and delete of a row. It uses [Hibernate Envers](https://hibernate.org/orm/envers/) and keeps the values after each change, row by row, in history tables (the values before a change are those of the previous history entry). It is part of `ecuacion-splib-jpa`, and an application enables it by adding the dependency on Hibernate Envers.

Applications that do not add the dependency on Hibernate Envers behave exactly as before.

The record of operations themselves (when, who, which operation) is the [audit log](page?id=core/audit/audit-log&lang=en). With both enabled, the rows an operation changed, and how, can be traced from `operationId` of the audit log. Either one can also be enabled alone.

## Enabling it

### pom.xml

Add the dependency on Hibernate Envers. `ecuacion-splib-jpa` depends on Hibernate Envers optionally, so applications that do not use it do not get it. Its version is managed by Spring Boot, so it need not be written.

```xml
<dependency>
  <groupId>org.hibernate.orm</groupId>
  <artifactId>hibernate-envers</artifactId>
</dependency>
```

### Turning it off

To turn it off while keeping the dependency on Hibernate Envers (in tests and so on), use Hibernate's setting. Then `@Audited` is ignored, and no history table is created.

```properties
spring.jpa.properties.hibernate.integration.envers.enabled=false
```

### Entities

Put `@Audited` (`org.hibernate.envers.Audited`) on the entities whose history is kept. When an entity inherits common columns from a superclass (`@MappedSuperclass`), put it on the superclass too. Put `@NotAudited` on columns not to be kept in the history. For the entities generated by `ecuacion-tool-code-generator`, these annotations are added by specifying, in the DB column definitions (Excel), the tables whose history is kept and the columns left out.

```java
@Entity
@Audited
public class Inquiry extends SystemCommon {

  // a column not kept in the history
  @NotAudited
  private String memo;
  ...
}
```

A relation from an entity with `@Audited` to an entity without it needs `@Audited(targetAuditMode = RelationTargetAuditMode.NOT_AUDITED)`. Without it, the application fails to start. When writing entities by hand, put these yourself too.

### Entity scan

The application is expected to specify the package of its own entities with `@EntityScan` (the `BaseConfig` generated by `ecuacion-tool-code-generator` does). When enabled, `DataChangeRevision`, which holds the revision information, is added to that scan.

## What is recorded

### History tables (`<table>_aud`)

For each entity with `@Audited`, a table named after the original table with `_aud` appended is created. Every insert, update and delete of a row adds one row holding the values of that row after the change.

| Column | Content |
| --- | --- |
| The primary key of the original table | The primary key of the changed row. |
| `rev` | The number of the revision, the unit grouping changes.<br>It joins to `rev` of the `revinfo` table. |
| `revtype` | The kind of the change.<br>`0` is an insert, `1` an update and `2` a delete. |
| The columns of the original table | The values after the change.<br>`null` for a delete. |

### The revision table (`revinfo`)

The changes made in one transaction make one revision.

| Column | Content |
| --- | --- |
| `rev` | The number of the revision. |
| `revtstmp` | When the changes were made (the server's time zone).<br>Envers' default is a number of milliseconds, but it is a date-time column here so that `ecuacion-tool-housekeep-db` can delete old history. |
| `operation_id` | The ID of the operation that made the changes.<br>The same value as `operationId` of the operation's audit log record. |
| `actor` | Who made the changes.<br>Like `actor` of the audit log, `Authentication#getName()`. |
| `original_actor` | During a switch user only, the administrator.<br>The same as `originalActor` of the audit log. |

`operation_id`, `actor` and `original_actor` are taken while a request to a controller method is processed (including requests the audit log does not record). For changes made elsewhere (batch, inside the login process, work handed off to another thread with `@Async` and so on), the history is kept but these columns are `null`.

## Creating the tables

When tables are created automatically, with `spring.jpa.hibernate.ddl-auto=update` and so on, the history tables and the `revinfo` table are created too. When DDL is written by hand, prepare the DDL of these tables as well (the tables created with `ddl-auto=update` can serve as a reference).

## Changes that are not recorded

Only changes made through JPA entities are recorded. The following are not:

- Bulk `update` / `delete` in JPQL or SQL (queries with `@Modifying`, etc.)
- Changes made without JPA, such as with JDBC

## Deleting old history

With `ecuacion-tool-housekeep-db`, make the `revinfo` table the target (`rev` as the ID column, `revtstmp` for the date condition) and each history table a related table (joined by `rev`), and old revisions are deleted together with their history rows. A history table has a two-column primary key (the original table's primary key and `rev`), so it cannot be a target by itself.

## Personal data

History tables keep the values after each change as they are. Removing personal data from the original row leaves the values before the removal in the history.

- Leave columns whose history need not be kept out of the history with `@NotAudited` (see "Entities" above).
- When the personal data has to be removed from the history too, delete or rewrite the history rows of that row in the application. The "update" task of `ecuacion-tool-housekeep-db` works on tables with a single ID column only, so it cannot be used on history tables.
