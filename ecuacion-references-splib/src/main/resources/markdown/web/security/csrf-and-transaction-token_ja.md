`ecuacion-splib-web` は独立した2つの仕組みを重ねて使っています。1つはSpring Securityの標準的なセッションベースのCSRF保護（デフォルトのまま有効です。`SplibWebSecurityConfig` はこれを無効化していません。これは、ambient credentialに依存しないために無効化している `ecuacion-splib-rest` の `/api/**` エンドポイントとは対照的です）。もう1つは、フォームの二重送信を検出する、ワンタイムの**トランザクショントークン**という別の仕組みです。

## CSRFが既に有効なのに、なぜ別途トランザクショントークンが必要なのか

CSRF保護が防ぐのは、**別のサイト**がユーザーになりすましてリクエストを偽造することです。ユーザー**自身**のブラウザが**同じフォーム**を2回送信すること、例えばSubmitボタンの二重クリックや、ブラウザの戻るボタンで古いページに戻って再送信すること、については何も防いでくれません。トランザクショントークンはまさにこのケースのために存在します。ワンタイムの値なので、たとえ有効なCSRFトークンを伴っていても、同じトランザクショントークンを使った2回目の送信は拒否されます。

## 仕組み

1. `SplibControllerAdvice#modelAttribute` が、`@RestController` 以外のすべてのリクエストで新しいトークン（`TransactionTokenUtil#issueNewToken`）を発行し、モデルに追加します。これにより、レンダリングされるすべてのフォームが、ランダムな40文字のトークンを隠しフィールドとして持つことになります（`@RestController` のエンドポイントは完全にスキップされます。この仕組みはThymeleafでレンダリングされるフォームにのみ適用されます）。
2. 発行されたトークンはセッション内の `Set` に保持されます（フォームごとではなくセッションごとに1つの集合）。そのため、複数のページを同時に開いても、互いのトークンを無効化することはありません。
3. 送信時、`SplibControllerPrepareHelper#transactionTokenCheck` が、フォームとともに送信されたトークンをセッションの集合と照合します。集合に見つからないトークン（既に消費済み、または発行されていない）は `BusinessViolation` を発生させ、他のバリデーションエラーと同じように処理されます（[例外処理](page?id=web/exception-handling&lang=ja)を参照）。一致したトークンは即座に集合から削除されるため、2回目の送信に再利用することはできません。
4. リクエストがサーバーサイドのフォワード（`forward=true`）である場合、このチェックは完全にスキップされます。フォワードは元のリクエストのパラメータをすべて引き継ぐため、これがないと同じリクエストに対してこのチェックが2回走ってしまいます。

## セッションごとの上限

トークンはフォームが実際に送信されて初めて削除される仕組みのため、送信せずに新しいページを次々に要求し続けるセッション（例えば `permitAll` なページへの連続した `GET`）があると、このセッションスコープの集合に上限なくトークンが蓄積してしまいます。これを防ぐため、`TransactionTokenUtil` はセッションあたりのトークン数を10個に制限しています（`TransactionTokenUtil.MAX_TOKENS_PER_SESSION`）。上限に達すると、最も古いトークンから破棄されます（この目的のため `LinkedHashSet` で挿入順を保持しています)。これにより、同一セッションで複数タブを同時に開いておく程度の余裕は残しつつ、トークンを無制限に発行させる攻撃によるメモリコストをセッションごとに一定に抑えています。
