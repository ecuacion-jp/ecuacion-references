`SplibWebConfig` は（[クイックスタート](page?id=web/quickstart&lang=ja)にあるように `jp.ecuacion.splib.web.config` がコンポーネントスキャンされていれば）すべてのリクエストに対して自動的に `LoggingInterceptor` を登録し、2つの安全策を適用します。これにより、DEBUGログを有効にすること自体が資格情報の漏えいにならないようにしています。

## リクエストパラメータのマスキング

すべてのリクエストは、そのパラメータ（URIとパラメータ一覧）とともにDEBUGレベルでログに出力され、実際にリクエストに何が含まれていたかを追跡するのに役立ちます。しかし、リクエストパラメータは完全にクライアントが指定するものであり、これがないとログインやパスワード変更の送信で、パスワードの平文がそのままログファイルに残ってしまいます。名前に `password` という文字列が（大文字小文字を区別せず）どこかに含まれるパラメータ、例えば `login.password`、`adminLogin.password`、`builtinAdminLogin.password`、はすべて、値をログに出す代わりに `***` に置き換えられます。これは命名規約に基づく仕組みです。このライブラリ内、そしてこのライブラリの上に構築されるアプリケーションの慣習として、パスワード用のフィールドはすべてキーのどこかに「password」を含む名前を付けることになっています。

## セッションIDの切り詰め

すべてのログ行の先頭にあるプレフィックスは、セッションIDの**末尾8文字のみ**でセッションを識別し、完全な値は決して出力しません。セッションIDはベアラー型の資格情報であり、それを入手した者はパスワードなしでセッションを乗っ取ることができます。このプレフィックスはすべてのリクエストでDEBUGレベルとして出力されるため、完全なIDをログに出してしまうと、ログファイル自体がセッションハイジャックの材料が漏えいする場所になってしまいます。末尾8文字であれば、1つのログファイル内で同一セッションに属する行同士を関連付けるには十分です。

## セッションIDをURLに出さない

ロギングとは別に、`SplibWebConfig` はサーブレットコンテナのレベルで `SessionTrackingMode.COOKIE` も設定しており、セッションIDは常にCookieのみで運ばれ、`;jsessionid=...` のようにURLへ付加されることはありません。これは主にロギングの観点ではありませんが、同種のリスクが当てはまります。URLに漏れ出たセッションIDは、ブラウザの履歴・アクセスログ・他サイトへ送られる `Referer` ヘッダーに残ってしまいます。いずれも、Cookieのみで運ばれるセッションIDであれば決して届かない場所です。加えて、`;jsessionid=...` という接尾辞はSpring SecurityのURLファイアウォールに「潜在的に悪意のある」文字として拒否されることもあり、これがデフォルトで無効化されているもう一つの独立した理由になっています。
